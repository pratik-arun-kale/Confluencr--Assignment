# Assumptions

These are the interpretations I made where the brief left a choice open.

## Accounts

1. **IDs are UUIDv4 strings, generated by the server.** Clients cannot choose them.
2. **Sending `balance` (or `id`, `created_at`) when creating an account is rejected** with
   `400 VALIDATION_ERROR` rather than silently ignored. The brief says the client "should not
   be allowed to set the initial balance", and an explicit error makes that visible. Unknown
   fields are rejected on every endpoint for the same reason.
3. **Names** are trimmed of surrounding whitespace and must be 1–100 characters. Names do not
   need to be unique, because two people can share a name.

## Money

4. **Currency:** a single currency, with amounts in major units and **2 decimal places**
   (e.g. rupees and paise).
5. **Inputs with more than 2 decimal places are rejected** (`400`), never rounded. Rounding
   money silently is a correctness bug.
6. **Amounts are returned as strings** (`"150.00"`) to avoid float precision loss in clients.
   Requests accept either a string or a JSON number.
7. **Limits:** a single transaction or transfer is capped at `1,000,000,000.00`, and a balance
   at `9,999,999,999,999,999.99` (the `NUMERIC(18,2)` maximum). A credit that would exceed it
   returns `422 BALANCE_LIMIT_EXCEEDED`.
8. **A debit equal to the full balance is allowed** (the balance becomes `0.00`). Overdrafts
   are never allowed.

## Transactions

9. **Rejected transactions are not stored.** Only successful transactions appear in the
   ledger and history, so "balance = sum of all valid transactions" holds directly.
10. **`reference_id`** is a client-chosen string of 1–100 characters, trimmed, and
    case-sensitive (`INV-1` and `inv-1` are different references).
11. **A duplicate `reference_id` returns `409`.** An identical retry gets
    `DUPLICATE_TRANSACTION`, and the response includes the original transaction. Reusing the
    reference with a different type, amount or description gets `REFERENCE_ID_CONFLICT`. In
    both cases nothing is written.
12. **`description` is optional** (up to 255 characters). It is part of the payload that is
    compared when detecting an identical retry.
13. **Timestamps are UTC**, generated by the database at insert time.
14. **"Latest first"** is by `created_at` descending. Ties are broken by insertion order.

## History

15. **Defaults:** `page=1`, `limit=20`, maximum `limit=100`. A page beyond the last returns an
    empty list with correct metadata rather than an error. Invalid values (`page=0`,
    `limit=500`, non-integers, an unknown `type`) return `400 VALIDATION_ERROR`.
16. History includes transfer legs. They can be recognised by a non-null `transfer_id`.

## Transfers (bonus)

17. **A transfer is stored as a `transfers` record plus two ordinary ledger entries:** a debit
    on the source and a credit on the destination. Both are linked by `transfer_id` and have
    `reference_id = "TRF-{transfer_id}"`.
18. **A transfer's `reference_id` is unique per source account** and is separate from
    transaction references. A transfer may use `INV-1` even if a direct transaction on the
    same account already uses it.
19. **A transfer to the same account** is rejected with `400 SAME_ACCOUNT_TRANSFER`.

## Errors and status codes

20. `400` means malformed or invalid input. `404` means a well-formed ID that doesn't exist
    (a malformed ID gets `400 INVALID_ACCOUNT_ID`). `409` means a duplicate. `422` means a
    valid request that the current ledger state does not allow (insufficient balance).
    FastAPI's default use of 422 for validation errors is deliberately changed to 400 so
    that these two cases stay distinct.
21. If an account stays locked by concurrent operations for longer than
    `DB_LOCK_TIMEOUT_MS` (default 5 s), the request returns `503 LOCK_TIMEOUT` with
    `Retry-After`, and nothing is written.

## Scope

22. **No authentication or authorisation**, because the brief does not ask for it. Any caller
    can act on any account. See DESIGN.md §9.
23. **Accounts cannot be deleted or renamed.** The brief only asks for creation, and deleting
    an account would conflict with keeping the ledger immutable.
